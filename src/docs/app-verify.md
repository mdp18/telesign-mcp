# App Verify API

The Telesign App Verify API verifies a phone number from inside a mobile app using a flash call:
Telesign places a short voice call to the handset, and the caller ID of that call is the secret. The
caller ID is a fixed prefix followed by five or six randomly generated digits, and those last digits
are the verification code. Nobody answers the call; the code is read from the caller ID, either
automatically by the app or by the user from their missed calls. Because no SMS is sent and nothing has
to be answered, verification is fast and low-friction.

This guide also covers the Smart Verify API, a separate one-call OTP product, in the second part.

## When to use it

Two ways to use the flash call:

| Mode | Platform | How the code gets back |
| --- | --- | --- |
| Frictionless App Verification | Android only | The app reads the incoming call's number from the call log, strips the prefix and submits the code with no user action. Requires permission from Google to access call logs, which Google restricts in most cases. |
| Missed Call Verification | Any handset | The user opens their missed calls, reads the last five or six digits of the number and types them into your app. |

Use App Verify when the user is on a phone that can receive a circuit-switched voice call and you want
to avoid SMS delivery.

Use something else when:

- The device cannot receive voice calls (for example a data-only tablet) or the user will not give a
  mobile number: use `sms-verify`, `voice-verify` or `verify-api`.
- You want zero interaction without call-log permissions: see `silent-verify`.
- You want Telesign to choose between SMS and a voice call for an ordinary OTP: see the Smart Verify
  API section below, or `verify-api` for omnichannel verification with fallback.

## How it works

Terms: the **caller ID** is the number Telesign calls from; the **prefix** is its first digits; the
**verify code** is its last five or six digits, randomly generated by Telesign. Whether codes are five
or six digits long is configured for your account by Telesign Customer Support.

1. The user enters their mobile number in your app; the app sends it to your server.
2. Your server calls `appverify_initiate` with the number. The response contains `reference_id`,
   `prefix` and `verify_code`. Send the **prefix** to the app so it can recognize the verification
   call. Keep `verify_code` on the server.
3. Telesign calls the number from a caller ID made of the prefix plus the code. Calls from numbers
   that do not start with the prefix are ordinary calls and the app must let them through.
4. The code is extracted from the caller ID: automatically by the app (frictionless), or typed in by
   the user from the missed call (missed call verification). The app sends it to your server.
5. Your server compares the received code with the `verify_code` it stored, then calls
   `appverify_finalize_call` with the `reference_id` and the code. Telesign compares it with the code
   it generated and returns success or failure. Finalize also terminates the call; Telesign recommends
   that the app end the call on the handset too. If no finalize arrives, the call is cancelled after a
   short period. Ending the call quickly avoids voicemail pickup and unnecessary call charges.
6. If something went wrong, report it so Telesign can troubleshoot: `appverify_report_caller_id` when a
   call arrived but its caller ID did not match the prefix, `appverify_report_timeout` when no
   verification call reached the handset in time.
7. `appverify_get_status` returns the transaction status at any point and can be called repeatedly.

Finalize **once** per transaction. A second finalize for the same `reference_id` returns an error
(`Invalid App Verify API finalize`, code `-30014`) and invalidates the transaction.

### What an AI assistant can and cannot do with App Verify

An assistant can call every endpoint, but the product is designed around an app on the handset that
screens the incoming call. Without such an app, an assistant can still run a missed-call verification
conversationally: call `appverify_initiate`, ask the user to read the last digits of the number that
just called them, compare with `verify_code`, and call `appverify_finalize_call`. In that case never
reveal `verify_code` or the full expected caller ID to the user - the user must supply the digits.
Frictionless verification is impossible without the customer's Android app.

## MCP tools

| Tool | What it does | Endpoint |
| --- | --- | --- |
| `appverify_initiate` | Starts verification: Telesign flash-calls the number from a caller ID containing the code. | `POST https://rest-ww.telesign.com/v1/verify/auto/voice/initiate` |
| `appverify_finalize_call` | Submits the code read from the caller ID, gets the result and ends the call. | `POST https://rest-ww.telesign.com/v1/verify/auto/voice/finalize` |
| `appverify_report_caller_id` | Reports a call whose caller ID did not match the expected prefix. | `POST https://rest-ww.telesign.com/v1/verify/auto/voice/finalize/callerid` |
| `appverify_report_timeout` | Reports that the verification call never reached the handset in time. | `POST https://rest-ww.telesign.com/v1/verify/auto/voice/finalize/timeout` |
| `appverify_get_status` | Returns the status of a transaction. | `GET https://rest-ww.telesign.com/v1/verify/auto/voice/{reference_id}` |
| `smartverify_send_code` | Smart Verify API: sends an OTP by SMS or voice, whichever Telesign judges most effective. | `POST https://rest-ww.telesign.com/v1/verify/smart` |

Use `docs_get_tool_reference("appverify_initiate")` (or another tool name) for the full generated reference.

## Quick start

Start a verification (`appverify_initiate`). Returns `reference_id`, `prefix`, `verify_code` and
`status.code` 2400 (Pending).

```json
{ "phone_number": "15551234567" }
```

Start with device details and a wait time (all optional).

```json
{
  "phone_number": "15551234567",
  "verification_timeout": 30,
  "carrier": "Example Mobile",
  "is_voice_capable": "1",
  "is_roaming": "0"
}
```

Finalize with the digits read from the caller ID (`appverify_finalize_call`). Returns `status.code`
2401 (Success) when the code matches.

```json
{
  "reference_id": "0123456789ABCDEF0123456789ABCDEF",
  "verify_code": "20085"
}
```

Check the transaction (`appverify_get_status`). Returns the current `status`.

```json
{ "reference_id": "0123456789ABCDEF0123456789ABCDEF" }
```

Report a call that came from an unexpected number (`appverify_report_caller_id`). Returns
`status.code` 2407.

```json
{
  "reference_id": "0123456789ABCDEF0123456789ABCDEF",
  "unknown_caller_id": "445550100363"
}
```

Report that no call arrived (`appverify_report_timeout`). Returns `status.code` 2409.

```json
{ "reference_id": "0123456789ABCDEF0123456789ABCDEF" }
```

## Key parameters

`appverify_initiate`:

| Parameter | Notes |
| --- | --- |
| `phone_number` (required) | The end user's number including country code, digits only. It should be the number of the handset the app runs on. |
| `verification_timeout` | Seconds the handset will wait for the verification call after a successful initiate response. The call time is limited to 45 seconds. |
| `verify_code` | Supply your own code instead of a Telesign-generated one (the reference says it should be five digits). The feature must be enabled by Telesign Customer Support. |
| `carrier`, `connection_type`, `device_icc`, `device_phone_number`, `is_roaming`, `is_voice_capable`, `network_type`, `os_version`, `platform_version` | Optional information about the device and its network, collected by the app. |

`appverify_finalize_call`:

| Parameter | Notes |
| --- | --- |
| `reference_id` (required) | From the initiate response. |
| `verify_code` | The code parsed from the caller ID shown on the device. The API marks it optional, but it is what Telesign compares to decide success, so send it. |

`appverify_report_caller_id` takes `reference_id` and `unknown_caller_id` (both required; the caller ID
that was not recognized) and an optional `customer_id`. `appverify_report_timeout` and
`appverify_get_status` take only `reference_id`.

## Responses and status codes

All App Verify responses share the same structure:

| Field | Meaning |
| --- | --- |
| `reference_id` | 32-character hex ID of the transaction. Needed for every later call. |
| `sub_resource` | Which operation answered: `auto_verify_initiate`, `auto_verify_finalize`, `auto_verify_finalize_unknown`, `auto_verify_finalize_timeout`, or `app_verify_api` for status. |
| `status.code`, `status.description`, `status.updated_on` | The transaction status. Code against `status.code`, not the HTTP status. |
| `errors[]` | `code` and `description` for each error; empty on success. |
| `prefix` | Initiate only. The first digits of the caller ID; remove them from the caller ID to get the code. |
| `verify_code` | Initiate and finalize. The verification code. |
| `resource_uri` | Not needed; ignore it. |

Transaction status codes:

| Code | Description | What to do |
| --- | --- | --- |
| 2400 | Pending | Normal after initiate. Wait for the call, then finalize. |
| 2401 | Success | The number is verified. |
| 2402 | Failure | The code did not match. Treat as not verified. |
| 2403 | Not Attempted | No call was attempted. |
| 2404 | Invalid Phone Number | Ask the user to correct the number. |
| 2405 | Not Supported | Use another verification method. |
| 2407 | CallerID prefix did not match | Returned after reporting an unknown caller ID. |
| 2408 | Unsupported phone type | The number cannot receive a flash call (not a suitable mobile). Fall back to another method. |
| 2409 | Verification call not received | Returned after reporting a timeout. Retry or fall back. |
| 2410 | Please retry verification | Start a new transaction. |
| 2411 | Verification call failed | Retry or fall back. |
| 2429 | Call blocked by customer request | The destination is blocked by your own settings. |
| 2430 | Call blocked by Telesign | The destination is blocked by Telesign. |

Error codes (in `errors[]`):

| Code | HTTP | Meaning |
| --- | --- | --- |
| -10001 | 400 | Not allowed host (your IP address is not authorized), or unsupported product name |
| -30002 | 400 / 401 | Account not activated |
| -30003 | 400 / 401 | Account limit reached |
| -30014 | 400 | Invalid App Verify API finalize (for example a second finalize for the same transaction) |
| -40006 | 400 | Bad request |
| -40007 | 400 | Rate limit exceeded |
| -40022 | 400 | App Verify API not supported |
| -50059 | 400 | Status not available (`appverify_get_status`) |
| -10009 | 401 | Invalid source IP address |
| -20002 | 401 | Product not enabled for this Customer ID |
| -20003 | 401 | Feature not enabled for this Customer ID |
| -40002 | 401 | Not authorized |
| -40004 | 404 | Resource not found |
| -10004 | 404 | Reference ID expired (`appverify_get_status`) |
| -40005 | 405 | Method not allowed |
| -40008 | 429 | Transaction hard cap exceeded; request denied |
| -90001 | 503 | System unavailable; try again later |

## App design and security practices

- Never ship Telesign credentials inside the app; anyone can disassemble it. All Telesign calls go
  through your server, and the app talks to your server over a secure channel.
- Check the code on your server before calling finalize. Do not send the verification code to the
  device for validation.
- Ask for the number of the device the app is installed on, and for the cellular connection to be on.
  Attempt flash-call verification only on devices that can receive a circuit-switched voice call.
- Collect country code and phone number in separate fields; a single field invites mistakes such as a
  leading `0` or `+`.
- Do not rely on auto-extracting the phone number from the device; it is inconsistent across carriers
  and locales. If you offer it, let the user edit the number.
- Tell the user a verification call is coming and that they should ignore it rather than answer.
- Offer an alternative (`sms-verify`, `voice-verify`) for users who cannot or will not use a mobile number.
- Missed call flow: ask for the number, explain what will happen with options to retry or continue,
  show the caller ID pattern with blanks for the last five or six digits, let the user enter them,
  then verify.

Android permissions for the frictionless mode: `android.permission.READ_PHONE_STATE` (the user must
grant it; used to detect the flash call), `android.permission.CALL_PHONE` (bundled with the previous
one; used to cancel the call), `android.permission.INTERNET`, `android.permission.ACCESS_NETWORK_STATE`
and `android.permission.READ_CALL_LOG` (to read the code from the call log; needs Google's approval).
Missed call verification needs none of the call-log permissions. Follow current Android guidance,
because permission rules keep tightening.

## Requirements and limits

- App Verify must be added to the account by Telesign and is available to full-service accounts only.
- Code length (five or six digits) is set up by Telesign Customer Support; supplying your own
  `verify_code` is a separately enabled feature.
- Requests are `application/x-www-form-urlencoded`, UTF-8; authentication is Basic or Digest. The MCP
  tools handle the encoding.
- The verification call is limited to 45 seconds.
- One finalize per transaction; status can be queried many times. A reference ID eventually expires
  (`-10004`).
- Default per-product rate limits apply; there is also a transaction hard cap (`-40008`).
- App Verify has no callbacks: results come from finalize and `appverify_get_status`.

## Smart Verify API

The Smart Verify API sends a one-time passcode to a phone number in a single call and lets Telesign
decide whether an SMS or a voice call is the most effective way to deliver it. By default the service
selects SMS and falls back on a voice call, so you do not have to build the channel choice yourself.

Tool: `smartverify_send_code` - `POST https://rest-ww.telesign.com/v1/verify/smart`.

Minimal call. Returns `reference_id`, `sub_resource` (`sms` or `voice`, the channel actually used) and
a preliminary `status`.

```json
{ "phone_number": "15551234567" }
```

Custom wording, a use-case tag and a preferred channel.

```json
{
  "phone_number": "15551234567",
  "ucid": "ATCK",
  "preference": "Voice Verify",
  "language": "en-US",
  "tts_message": "Hello, your code is $$CODE$$. Once again, your code is $$CODE$$. Goodbye."
}
```

Smart Verify parameters:

| Parameter | Notes |
| --- | --- |
| `phone_number` (required) | Digits only, starting with the country dialing code. |
| `ucid` | Use-case code: `ATCK` (2FA on login or account update), `BACF` (account creation exposed to bulk attacks and fraudsters), `BACS` (account creation exposed to bulk attacks or spammers), `CHBK` (expensive or unusual purchase), `CLDR` (calendar event), `LEAD` (lead verification), `OTHR` (other), `PWRT` (password reset), `RESV` (reservations), `RXPF` (prescription fraud prevention), `SHIP` (shipping notification), `THEF` (preventing number deactivation or redirection for identity takeover), `TRVF` (money transfer approval), `UNKN` (same as `OTHR`). |
| `preference` | `SMS Verify` or `Voice Verify`. Overrides the automatic selection and asks Telesign to try that method. Telesign uses it whenever possible but may ignore it if the destination does not support it. |
| `sms_message` | Custom text used if the code is sent by SMS. The reference does not say how the code is placed in this text (the `$$CODE$$` placeholder is documented only for `tts_message`). |
| `tts_message` | Custom text-to-speech message used if the code is sent by voice. Include `$$CODE$$` where the generated code should be inserted. Set `language` whenever you use it. |
| `language` | Language of `tts_message`, from the Voice Verify text-to-speech language list. Without it US English is assumed; for an unsupported language Telesign may choose a default. |
| `ignore_risk` | Boolean. Listed in the API reference, but its published description duplicates the text of `preference`; confirm its behaviour with Telesign before relying on it. |

Smart Verify response fields:

| Field | Meaning |
| --- | --- |
| `reference_id` | 32-character hex ID of the request. |
| `sub_resource` | `sms` or `voice`: the channel the service used. |
| `status.code`, `status.description`, `status.updated_on` | Preliminary delivery status, for example `290` "Message in progress". Code against `status.code` and `errors[].code`, not the HTTP status. |
| `errors[]` | `code` and `description` of each error, for example `-10001` "Invalid Request: PhoneNumber Parameter". Empty when there are none. |
| `numbering`, `phone_type`, `carrier` | Optional number details (original and cleansed number, phone type, carrier name). Included only when Telesign Customer Support enables them. |

Things to know before choosing Smart Verify:

- The request body is `application/x-www-form-urlencoded` with Basic authentication.
- The Smart Verify reference documents only this one send operation. It does not describe a status or
  code-check endpoint, a way to supply your own code, or callbacks. If you need to generate or check
  the code yourself, track delivery, or control fallback explicitly, use `verify-api` (send with
  `verifyapi_send_otp`, check with `verifyapi_check_code`), `sms-verify` or `voice-verify`.
- HTTP statuses returned: 200, 400, 401, 404, 405, 429 and 503. Status and error code values follow
  Telesign's general lists; see `error-codes`.
